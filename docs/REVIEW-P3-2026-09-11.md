## 問題清單（依嚴重度排序）

### BLOCKING

#### B1. `LatinLexicon::complete()` 的 top-n heap 比較子寫反，n > 1 的結果幾乎全錯

- **位置**：`Source/Engine/MixedScript/latin_lexicon.cpp:236-238`（`worse` lambda）
  ＋ `:262-269`（heap 更新）
- **重現（引擎層，最小案例）**：掃描順序 (rank, word) = (9,`aaa`) (9,`aab`) (1,`aac`) (2,`aad`)，n=2
  → 得到 `aac, aab`；正確答案是 `aac, aad`。
- **重現（真實詞典）**：

  ```
  complete("th", 9) 實際 = throughput thad thaddeus thai thailand thais
                           thailander thailanders thalamencephalon
  complete("th", 9) 正確 = throughput than thank thanked thankful
                           thankfully thanking thankless thanks
  ```

  `than/thank/that/the/this/there/these` 的 rank 都是 300（tier 0），
  回傳的 `thad/thai/thailand` 是 302、`thailander` 之後是 304。
- **重現（真 KeyHandler，Shift+Tab 候選窗）**：

  ```
  'wh' -> whatsapp whacked whacking whacks whacker whackers whackings whacko whackos
  'pr' -> prompt practical practicalities practicality practically practicability ...
  'st' -> staging stabbed stabbing stabbings sta stabber stabbers stabile stabiles
  ```

  沒有 what/when/where/which/while、沒有 problem/project/provide、沒有 start/still/state。
- **成因**：`std::push_heap` / `pop_heap` 帶 comparator `comp` 時，`front()` 是 **comp 下的最大值**。
  `worse(a,b) = better(b,a)`，所以 comp 下的最大值是「最好的候選」而不是最差的。結果：
  `best.front()` 存的是目前最佳者，`else if (worse(best.front(), candidate))` 只在新候選
  **比最佳者還好**時才收，而 `pop_heap` 接著把那個最佳者踢掉換成新的。
  掃描到第 n 個之後的詞幾乎全被丟棄，最終結果 ≈「字母序前 n 個，其中一格反覆被換掉」。
  header 寫的「keeps only a size-n min-heap of the best candidates seen」與實作不符。
- **為什麼 n=1 沒事**：單元素 heap 的 front 同時是最好也是最差，比較子方向不影響。
  所以 tooltip（`complete(run,1)`）、`_isAlreadyCompleteWord`（`complete(word,1)`）、
  以及整份 eval（只看 top-1）全部正常——這就是它能過所有測試的原因。
- **為什麼現有 gtest 抓不到**：`CompleteOrdersByTierThenRankThenAlphabetical`、
  `CompleteOrdersUserWordsByCountDescending`、`CompleteTiesBreakAlphabetically`
  都是 `complete(..., 10)` 但只有 3 個候選，整趟掃描 `best.size() < n`，淘汰分支從未執行；
  `CompleteLimitsToN` 用 n=2 掃 5 個未標 rank 的詞，前兩個掃到的剛好就是正解；
  `CompletePerformanceOnRandomPrefixes` 完全不驗內容。
- **修法**：heap 改用 `better` 當 comparator（front 就是最差者），收件條件改成
  `better(candidate, best.front())`；並補一個「候選數 > n 且正解在掃描尾端」的 gtest。

#### B2. `latinLearnTypedWords` 把任何 3 字母以上的亂碼寫進 `latin-user.txt`，而且它們永遠排第一

- **位置**：`Source/KeyHandler.mm:1218-1227`（`_learnTypedLatinWordIfEligible:`）。
  三個閘門只有：偏好開著、`word.size() >= 3`、`IsAllAsciiLetters`。
  **沒有字典檢查、沒有長度上限。**（而 Rule-A run 本來就只可能含 a–z，
  所以 `IsAllAsciiLetters` 在這條路上實質是空檢查。）
- **實測寫入內容**（每個情境前都清空詞庫與記憶體 lexicon）：

  | 序列 | `latin-user.txt` | 說明 |
  |---|---|---|
  | `thq ` | `thq\t1` | 非字典詞，寫 |
  | `thq`+Enter | `thq\t1` | 寫 |
  | `zzq`+Enter | `zzq\t1` | 寫 |
  | `qwrt`×10 +Enter（40 字母）| 原字串`\t1` | **無長度上限** |
  | `thq,` | `thq\t1` | 標點邊界也寫 |
  | `thq5`+Enter | `thq\t1` | 數字是邊界，字母段照寫 |
  | `thq`+Esc | （空） | ✅ 不寫 |
  | `thq`+Backspace×3 | （空） | ✅ 不寫 |
  | Shift 大寫 `ABC`+Enter | （空） | ✅ 不寫 |
  | `coo `+Enter（Rule-B 中文提交）| （空） | ✅ 不寫 |
  | `th`+Enter（2 字母）| （空） | ✅ 低於下限 |
  | 純中文 `su3cl3`+Enter | （空） | ✅ 不寫 |
  | `thq `×2 | `thq\t2` | ✅ 計次正確 |
  | `aweso`+Tab+Enter | `awesome\t1` | ✅ 不重複計次 |
  | `latinLearnTypedWords=false` | （空） | ✅ 零寫入 |
- **後果一（自我下毒）**：不小心把打一半的字提交一次，那個前綴的補全就永久死掉。
  使用者詞的 `rank()` 恆為 0（`latin_lexicon.cpp:196-198`），所以
  `_isAlreadyCompleteWord("aweso")` 從此為真。實測：

  ```
  cold: 'aweso' tooltip = awesome
  打一次 'aweso ' -> lexicon=["aweso\t1"]
  now:  'aweso' tooltip = nil ；'aweso'+Tab buffer 仍是 'aweso'
  ```
- **後果二（錯字上位）**：打錯一次就變成該前綴的 top-1，永遠壓過整本字典。實測：

  ```
  cold 'thq' tooltip = nil
  打一次 'thqrst ' -> lexicon=["thqrst\t1"]
  now  'thq' tooltip = thqrst
  ```
- **後果三（黏合字串進磁碟）**：英文後面沒空白直接打中文會產生黏合 run，**而且會被學起來**：
  `th` + Tab(`throughput`) + `su3` → 組字區 `throughputsu`，`latin-user.txt` 多一行
  `throughputsu\t1`。
- **修法**：`_rememberLatinWord:` 前加 `lexicon->isWord(word)`（至少 `isPrefix`），
  並加長度上限（20，與 `build_lexicon.py` 自己的過濾規則一致）。

#### B3. `_isAlreadyCompleteWord:` 比的是 rank，於是把打完的常用字改寫成 tech-seed 詞

- **位置**：`Source/KeyHandler.mm:1290-1300`，判準是
  `lexicon->rank(word) <= lexicon->rank(topCompletion[0])`。
- **成因**：`LanguageModelManager.mm` 先載 tech-seed（rank 0–299）再載字典
  （tier 0–4 偏移成 rank 300–304），所以**任一** tech-seed 詞都贏過**任一**字典詞。
  凡是「打完的普通英文字」剛好是某個 tech-seed 詞的前綴，閘門就判定它「還沒打完」。
- **實測（真 KeyHandler）**：

  ```
  code : tooltip = codesign ⇥ ，Tab -> codesign
  test : tooltip = testflight ⇥ ，Tab -> testflight
  run  : tooltip = runway ⇥
  ```

  對照組（閘門有效的）：`the` / `acer` / `awesome` / `coo` / `app` / `api` / `google` /
  `than` / `chat` / `free` / `check` / `agent` / `draft` / `cat` / `dog` → Tab 是 no-op。
- 也就是說 fix #3 想保護的正是「打完的普通英文字」，但它只在排名剛好有利時才保護得到。
- **修法**：閘門改成「`lexicon->isWord(run)` 為真就不自動拉長」；真的想再拉長就設計成
  明確的第二次 Tab 手勢，而不是靠 rank 比大小。

#### B4. Shift+字母會靜默吞掉待處理的 Rule-A 英文段（P1 遺留，P3 放大）

- **位置**：`Source/KeyHandler.mm:569`
  `BOOL mixedScriptActive = [self _mixedScriptAvailable] && !input.isShiftHold;`
  Shift 按著時 :593 的 boundary-commit 分支整段跳過，tracker 裡待處理的 run
  從來沒被 flush 進 grid，接著 upstream 的 Shift-字母路徑把組字區清掉。
- **實測**：

  ```
  待處理 'th' + Shift+R -> buffer='' state=Empty committed=''
  latinCompletionEnabled=false 時結果相同（⇒ P1 遺留，非 P3 引入）
  補全候選窗開著時 + Shift+R -> 同樣全丟
  ```
- **真實情境**：打 `the API` —— `the` 鎖成 Rule-A run，按 Shift+A 的瞬間 `the` 不見了。
- **修法**：Shift-字母路徑執行前先 commit 待處理的 Latin run（或把 `isLatinLocked()`
  的前置檢查獨立於 `isShiftHold`）。

#### B5. 已完成詞／無補全的 run 上按 Shift+Tab，KeyHandler 不吃這個鍵，Tab 漏到應用程式

- **位置**：`Source/KeyHandler.mm:930-945` → `_handleLatinCompletionTabWithShiftHeld`
  回 NO → `_handleTabState` 的 `if (!_grid->length()) return NO;`
  （Shift 按著時 run 從未被 commit 進 grid，所以 grid 是空的）。
- **實測 `handleInput` 的回傳值**：

  ```
  'acer' + Tab        : handled=true
  'acer' + Shift+Tab  : handled=false   <-- Tab 進到應用程式
  'the'  + Shift+Tab  : handled=false
  'thq'  + Shift+Tab  : handled=false
  'th'   + Shift+Tab  : handled=true（有補全，開窗）
  空組字區 + Tab       : handled=false（正確）
  ```
- 實作者 commit message 把這件事寫成「Shift+Tab 在已完成詞上會 beep＝P3 前既有」。
  實測 `errorCallback` **沒有**被呼叫（err=0）；真正發生的是 IME 不 consume 這個鍵，
  組字區還有未提交英文的情況下 Tab 事件送給 host app（移動焦點／插入 tab 字元）。
  比 beep 嚴重。P1 遺留，但 P3 讓 `acer`／`the` 這種普通完成詞也會踩到。
- **修法**：`_handleTabState` 回 NO 之前，若 `_mixedScriptTracker->isLatinLocked()`
  就回 YES（無動作），至少不要把鍵放出去。

### NON-BLOCKING

#### N1. 排序只有 5 個粗桶＋字母序，而且字典塞滿專有名詞

- 141,697 個詞共用 5 個 tier（tier 0 就有 38,784 個），tie 之後是字母序，
  所以大多數前綴的 top-1 實質是「該 tier 裡字母序最前的詞」：`complete("the",1) = theater`。
- 詞表本身含大量專有名詞／品牌：`thad` `thaddeus` `thai` `thailand` `aachen` `aaliyah`
  `aalto` `zyuganov` `obama` `trump` `taiwan` `tokyo` —— 但
  `tools/lexicon/build_lexicon.py` 的 docstring 寫「`--categories=`（proper names、
  hacker slang 等都是另外的 SCOWL category，這裡刻意不要）」，與輸出不符。
- 這是 eval 只有 40.6% 的真正原因，也是 B1 的症狀特別刺眼的原因。

#### N2. `BASELINE.md` 的「不可補全 46.7% 幾乎全是專有名詞／縮寫」不正確

- 同一份 154 個 never-completable token，我重跑分類：

  | 類別 | 數量 |
  |---|---|
  | 原文有大寫 **且** 小寫form 是字典詞（被誤分成專有名詞）| **61** |
  | 原文有大寫且不是字典詞（真專有名詞／縮寫）| 51 |
  | 小寫且不是字典詞 | 8 |
  | 小寫且是字典詞（報告已歸為 "other"）| 34 |

- 被誤分的 61 個包含：`API App Apple Analytics Blog CLI Community Consultant
  Electron Family Founder GPU Games Inc Link Meet More PRO RAG SLA SOW Sense
  Steam Story Stripe This Tool Tracker UTC` …
- 成因：`UncompletableCategory.classify`（`LatinCompletionKeyHandlerTests.swift:735-748`）
  先判 `hasUppercase` 才判 `isDictionaryWord`，大寫直接短路。
  `LanguageModelManager.isLatinWord(forTesting: "google") == true` —— 正如審查指令所疑，
  `Google` 應該算 ranking artifact 而非專有名詞。
- **真正的數字：95/154（62%）是排序失敗，不是字彙缺漏。** 只有 59 個（38%）真的不在字典裡。
  這把 P4 的工作方向從「換更大的詞表」改成「換一個真的頻率來源」。
- **修法**：`classify` 裡把 `isDictionaryWord` 判斷提到 `hasUppercase` 前面。

#### N3. 關掉 `LatinCompletionEnabled` 並不會停止寫磁碟

`_learnTypedLatinWordIfEligible:` 只檢查 `Preferences.latinLearnTypedWords`，
沒有檢查 `_latinCompletionAvailable`。實測：completion 關掉、learn 開著，
`thq ` 仍寫入 `thq\t1`。README 有寫正確的關法，但「把 P3 關掉」的直覺動作不會停止寫入。
建議一併 gate 在 `[self _latinCompletionAvailable]`。

#### N4. 測試會把暫存資料夾路徑留在**真實 plist** 裡，而且每跑一次就把它重建回來

- 審查開始前這台機器的實際狀態：

  ```
  UseCustomUserPhraseLocation = 1
  CustomUserPhraseLocation = /var/folders/.../T/mixime-completion-tests-E3398B87-...
  ~/Library/Application Support/McBopomofo/  -> No such file or directory
  ```

- 跑完一次全綠的 `xcodebuild test` 之後：**完全沒變**。因為兩個測試 class 都在 setUp
  讀走這個已被污染的值、在 tearDown 忠實地寫回去，污染會自我延續。
- 而且測試 host 啟動時 `+loadDataModels` 會照著 plist 解析
  `latinUserWordListPath` 並呼叫 `ensureLatinUserWordListFolder`，
  所以那個暫存資料夾每跑一次就被重建一次。
- **對 dogfood 的意義**：裝上去之後，使用者詞庫**和 `latin-user.txt`** 會寫進一個
  macOS 會清掉的暫存資料夾。
- P1 就有的 pattern（master 的 `MixedScriptKeyHandlerTests` 已經這樣寫），
  但 P3 多了一個 class 做同樣的事，使跨 class／跨 process 互相覆寫變得可能。
- **修法**：測試不要動真實 domain——用測試專屬的 `UserDefaults` suite，
  或 tearDown 一律還原成 `false` / `""` 而不是還原成「讀到的值」。

`Preferences.swift` 與 README 裡的隱私宣告目前沒有任何測試在守。

#### N6. 跑測試會弄髒 working tree

`testEval200LatinCompletion` 與 `testEval200ThroughKeyHandler` 都會改寫

#### N7. 三個規格落差

- 計畫檔 P3 設計寫「**Shift+Tab（或 ↓）** = 開候選窗列 top-N 補全」。↓ **沒實作**：
  實測 `th` + ↓ → 把 run commit 進 grid，開的是**一般 grid 候選窗**、只有一個候選 `["th"]`。
- `ChooseCandidateUsingSpace` 開著時，空白在補全候選窗裡**不會選字**：
  `th` + Shift+Tab + Space → 關窗、commit `th`、插一個字面空白（buffer `th `）。
  與 app 裡其他候選窗行為不一致。
- Shift+Tab **永遠碰不到 Rule-B 詞**：`_handleLatinCompletionOnCommittedNode`
  只在 `!input.isShiftHold` 時被呼叫，所以翻成英文的 Rule-B 節點只能用一般 Tab
  接受 top-1，沒有選擇的機會。

#### N8. 「從候選窗選一個補全」這條路徑在任何層級都沒有測試

`_handleLatinCompletionCandidateState:` 的選字鍵迴圈依賴活的 `VTCandidateController`。
測試 harness 沒有 delegate，於是數字鍵掉到「關窗並重新派送」，被當成注音鍵打進去：
實測 `th` + Shift+Tab + `1` → 組字區 `thㄅ`。
現有唯一的覆蓋是直接呼叫 `handler.acceptLatinCompletion(value:)`，
完全跳過按鍵、index 查找，以及 Swift delegate 裡
`selectedCandidate.reading == "_latin_completion_"` 那個分支。
實機 dogfood 前這條路徑等於沒驗過。

#### N9. 每鍵 tooltip 成本 ~0.3 ms，效能測試比真實詞典小 70 倍

- 真實 141,697 詞實測（M2 Max，-O2）：

  | 量測 | 值 |
  |---|---|
  | 10,000 隨機前綴 len=1 | 243 µs/次 |
  | len=2 | 11 µs |
  | len=3 / 4 | 0.5 µs / 0.3 µs |
  | `complete("c",1)` / `("s",1)` / `("co",1)` | 531 / 417 / 170 µs |

- 仍在規格的「每鍵 < 1 ms」之內，**不 blocking**。但兩個文件宣稱與實作不符：
  header 寫「O(k log n) … size-n min-heap」，實際是把整個匹配區間線性掃過去；

  實際只產生 26×26×3 = **2,028** 個詞，而且不驗內容。
- 便宜的改善：`_isAlreadyCompleteWord` 與 tooltip 各呼叫一次 `complete(run,1)`，
  合成一次即可砍半。

#### N10. 補全接受在「已提交節點」上時，一次 Backspace 刪掉整個詞

#### N11. 英文後面不打空白直接接中文，聲調鍵與整個音節會被吃掉

### 8. Eval 正確性

- **「有歷史」是否真的依語料順序學**：是。`testEval200LatinCompletion` 對每一 row
  先 `evaluate` 完該 row 的所有 token，才 `acceptLatinCompletion` 教進去，再進下一 row
  （`LatinCompletionKeyHandlerTests.swift:838-848`）。不是先全學再評。✅
  **但** 教的方式是 `handler.acceptLatinCompletion(value:)`，走的是「補全接受」路徑，
  不是 production 的 `latinLearnTypedWords` 路徑 —— 後者只有 **Rule-A** run 提交才會學，
  而語料裡相當比例的英文 token 是 Rule-B（P0.5 量到 25% 整詞都是合法中文讀音），
  實際打字時根本不會被學起來。所以「有歷史」的 48.8% 是**高估**。
- **小寫化是否也套在「專有名詞」分類上**：見 **N2**。`simulateCompletion` 確實先 `lowercased()`
  才模擬打字，但 `classify` 先判 `hasUppercase` 才判字典，所以 61 個「小寫是字典詞」的
  大寫 token 被誤歸成專有名詞。`isLatinWord("google") == true` 已確認。
- **平均省鍵的定義**：`max(0, tokenLength - k - 1)`，k＝top-1 首次等於目標詞的前綴長度，
  減 1 是接受補全的 Tab。不可補全者記 0，分母是全部 token（330）。定義合理且與表頭說明一致。
- **154 個不可補全 token 抽樣人工分類**（抽 20）：

  ```
  Games SOW mode PRD SLA Phison Iris PCClaw Sunny Tool
  Meet Tony per Lman EMBA Stripe PRO MOU Filco Tony
  ```

  其中 `Games / mode / Tool / Meet / Tony / per / Stripe / PRO / Iris / Sunny`（10 個）
  小寫形都在 SCOWL 裡 → 是**排序失敗**；
  `SOW / PRD / SLA / MOU / EMBA / PCClaw / Lman / Phison / Filco`（9 個）是真的縮寫／專有名詞。
  比例約 50:50，與全量統計（62% 排序失敗）方向一致 —— **報告的三分類不準確**。
