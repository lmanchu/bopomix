審查日期：2026-09-10 ／ 範圍：`git diff master..f1-mixed-script`（29 檔，含 20 萬行詞表）
審查方式：只讀。所有 probe／mutation 皆為暫時性，跑完已 `git checkout -- . && git clean -fd`，
`git status` 乾淨（本報告為唯一新增檔）。

## 發現 18 個問題（blocking 7／non-blocking 11）

## 結論：**不可 merge**

不是「修一修就好」的等級。這個分支在**純中文輸入**（完全沒有英文的情境）
把 eval200 中文段字元正確率從 **95.8% 打到 90.7%**，並且在功能自己的主要
使用情境（句中打英文詞 + 空白）會**靜默吞掉整句後面的內容**。而且
`mixedScriptEnabled` 預設 **true**，等於所有既有使用者升級後直接吃到全部退化。
分支自己 repo 裡既有的 4 個 upstream 測試現在是紅的——代表這個分支從未跑過
Xcode test suite。

### 「不可裝進系統日常使用」條件清單（全部滿足才可裝機 dogfood）

1. `Preferences.mixedScriptEnabled` 預設改為 **false**（P1 期間一律 opt-in）。
2. B1／B2 修好：Rule C 不得覆寫「letter run ≠ 該音節完整按鍵序列」的節點，
   且 `kMinAmbiguousWordLength` 至少提到 3。
3. B3 修好：Rule A run 後面的空白必須輸出空白字元，不得掉進候選窗分支。
4. B4／B5 修好：Esc 要清 reading buffer；backspace 把 locked run 刪空要解除 lock。
5. B6 修好：`handleForceCommit` 要涵蓋 pending Latin run。
6. `xcodebuild ... test` 全綠（現在 4 紅）。
7. 新增 KeyHandler 層級整合測試（目前 0 個），至少涵蓋本報告的 13 個 probe 情境。
8. `tools/eval` 的 space 處理必須與 app 一致，否則 F1 數字不得作為驗收依據。

#### B1. Rule C 把常用一聲中文音節換成英文字串（純中文退化 −5.1pt）
- **位置**：`Source/KeyHandler.mm:663-668`（`overrideCandidate` with `kOverrideValueWithHighScore`）
  ＋ `Source/Engine/MixedScript/mixed_script_tracker.cpp:49-63`（`onBoundary`）
- **重現**（`mixime-eval --mode keys`，OFF → ON）：

  | 按鍵序列 | `--mixed off` | `--mixed on` |
  |---|---|---|
  | `up ` | 因 | **up** |
  | `fu/ ` | 清 | **fu** |
  | `fu0 ` | 千 | **fu** |
  | `fu. ` | 秋 | **fu** |
  | `el ` | 高 | **el** |
  | `al ` | 貓 | **al** |
  | `ai ` | 摸 | **ai** |
  | `zo ` | 非 | **zo** |
  | `jo ` | 威 | **jo** |
  | `fu/ fu0 fu. ` | 清千秋 | **fufufu** |

  App 端同樣重現（PROBE04）：`up ` → 組字區 `up`；`fu/ ` → `fu`；`el ` → `el`。
  同一組按鍵在 `mixedScriptEnabled=false` 下是 因／清／高（PROBE11），
  證明是本分支造成，不是 upstream。
- **根因**：Rule C 只比對 `tracker.latinRun()`（**只有字母鍵**）是否在 20 萬字詞典裡，
  完全不檢查這串字母是不是該音節的**完整按鍵序列**，也不檢查該 reading 是否有
  真正的中文 unigram。掃過整份 `data.txt` 的單音節 reading，共 **20 個一聲 reading**
  的字母子串命中詞典（`up`=ㄧㄣ、`fu`=ㄑㄧ/ㄑㄧㄥ/ㄑㄧㄢ/ㄑㄧㄡ/ㄑㄧㄝ/ㄑㄧㄤ/ㄑㄧㄚ、
  `el`=ㄍㄠ、`al`=ㄇㄠ、`ai`=ㄇㄛ、`ak`=ㄇㄜ、`zo`=ㄈㄟ、`jo`=ㄨㄟ/ㄉㄨㄟ/ㄓㄨㄟ、
  `no`=ㄙㄟ、`ui`=ㄧㄛ、`tji`=ㄔㄨㄛ、`up`=ㄅㄧㄣ）。
  其中 19/20 是 2 字母 run。
- **修法一句**：Rule C 只在「letter run 長度 == 該音節完整 key sequence 長度」
  且 `kMinAmbiguousWordLength >= 3` 時才 promote；更保險的是 Rule C 的詞典限縮成
  `latin-tech-seed.txt` + 使用者詞庫，不要吃 20 萬字系統詞表。

#### B2. Rule C 連帶吞掉音節裡的非字母按鍵（真正的掉字）
- **位置**：同 B1。
- **重現**：`fu/ `（3 鍵）→ 輸出 `fu`（2 字元）——`/`（ㄥ）不見了。
  `1up `（3 鍵，賓）→ 輸出 `up`——`1`（ㄅ）不見了。
- **為什麼是獨立條目**：這直接違反分支自己宣稱的最高原則
  「never silently drop a keystroke」（`bopomofo_shape_tracker.h:60-67`）。
- **修法一句**：同 B1 的長度相等檢查，或在 promote 前把非字母鍵也記進 run。

#### B3. Rule A run 後打空白 → 開候選窗 → 之後每個字母被靜默丟棄
- **位置**：`Source/KeyHandler.mm:526`（rule A 清空 `_bpmfReadingBuffer`）
  → `:724-762`（空 buffer + 空白 → 候選窗）→ `:2225`（候選狀態下字母鍵 `errorCallback(); return YES;`）
- **重現**（app，PROBE03／PROBE13）：

  | 輸入按鍵 | eval CLI `--mixed on` 宣稱 | 真實 KeyHandler |
  |---|---|---|
  | `acer api gmail` | `acerapigmail` | **`acer`**（`api gmail` 全沒了） |
  | `ji3 up jo4` | `我up位` | **`我`** |
  | eval200 第 1 列完整 keys | `ㄟtokendashboard可以看出雲地整合少了多少token以提供如復健ㄒ` | **`ㄟtoken`** |

- **根因**：Rule A 觸發時 `_bpmfReadingBuffer->clear()`，之後的空白鍵讓
  `_bpmfReadingBuffer->isEmpty()` 為真且 state 是 `NotEmpty` → 走進
  `chooseCandidateUsingSpace`（預設 true）的候選窗分支；候選狀態下
  `InputModeBopomofo` 的字母鍵一律 `errorCallback(); return YES;` 被吃掉。
  `mixedScriptEnabled=false` 時 buffer 不是空的（存著 ㄐ），空白會 compose，
  所以**這條路徑是 P1 新造成的**（PROBE11：OFF 下 `acer` + 空白 + `api` → `ㄐㄇㄛ`，鍵沒被吃）。
- **影響**：這是本功能的主要使用情境（句中打英文詞、用空白分隔）。使用者會
  看到「打完 acer 按空白，跳出一個只有 acer 的候選窗，接下來打什麼都沒反應」。
- **修法一句**：Rule A run 被空白結束時，直接把 run 與一個字面空白一起送進 grid
  並 `return YES`，不要 fall through 到空白的候選窗分支。

#### B4. Esc 不再清 reading buffer，殘留的注音會混進下一個音節

- **修法一句**：該分支加上 `_bpmfReadingBuffer->clear();`，或把條件收斂成

#### B5. Backspace 把 locked run 刪到空，`latinLocked_` 沒解除 → 之後的中文鍵全變英文

### 3. `LatinPassthroughLM` 共用與競態 — **無競態，但零測試覆蓋**

- **執行緒**：`KeyHandler.mm` / `LanguageModelManager.mm` 內 grep 不到任何
  `DispatchQueue` / `dispatch_async` / `NSThread`；IMK 的 key event 在 main run loop
  串行送達，`registerAlternate` → `insertReading` → `clearKey` 之間全是同步呼叫
  （`_walk`、`_userOverrideModel->suggest`、`overrideCandidate`），沒有 re-entrancy 點。
  結論：**單執行緒假設成立，沒有跨 client 插隊的競態**。
- **`clearKey` 時機**：`ReadingGrid::insertReading()`（`reading_grid.cpp:52-73`）在建立
  `Node` 時就把 unigrams **move 進 Node**，之後 `update()`（:340-369）對已存在的
  節點會走 `hasNodeAt()` 直接跳過重查（:358），所以 `clearKey` 之後
  `_latin_` 節點不會因為後續插入而被重建成空 → 候選窗看得到 Latin 候選。**這點設計是對的。**
- **兩個連續 Latin 詞共用 `_latin_` key**：不會互相覆蓋，因為
  `registerSoleEntry` → `insertReading` → `clearKey` 在同一次呼叫內完成，
  節點已快照。實測 `gmail acer ` → `gmailacer`（值都在，只是空白問題見 B3）。
- **風險**：`- (void)clear`（`:328-335`）會 `mixedScriptLM().clear()` 掉**行程共用**的 LM。
  目前無害（entry 生命週期只有一次 key event），但這是靠時序而非結構保證的，
  而 mutation M4（把 `clearKey` 改成 no-op）**156 個測試全過**——這條保證完全沒有測試。

### 4. Tab 與候選窗 — **設計預期與實際不符**

- **Rule B 的 alternate 不在第 2 列，在最後一列**。
  `ReadingGrid::candidatesAt()`（`reading_grid.cpp:210-236`）只用 `stable_sort` 依
  **span 長度**排 node，node 內的 unigram 順序來自
  `ScoreRankedLanguageModel::getUnigrams()`（:596-603）的**分數降冪**——
  −99 必然墊底。`latin_passthrough_lm.h:47-51` 的註解說
  "candidatesAt() ... sorts by score independently of insertion order" 因此推論錯誤。
- **距離量測**：`data.txt` 單音節候選數 ㄧㄣ=51、ㄑㄧ=72、ㄍㄠ=39、ㄈㄟ=24
  （還要再加上跨音節長 node 的候選，那些排更前面）。
- **Tab cycling 實測**（PROBE09）：`ji3` + `up ` → `我up`（Rule C 已 override）
  → Tab×1 `我因` → Tab×2 `我音` → Tab×3 `我陰`。
  也就是**從英文 Tab 回中文只要 1 下（因為英文排最後、`currentIndex++` 會 wrap）**，
  但**從中文 Tab 到英文要按到底（50~70 下）**。Rule B「打完再 Tab 切英文」的
  設計承諾在實務上不成立。
- **誤學風險（`IsAllAsciiLetters`）— 實測為低**：掃過整份 shipped `data.txt`，
  **長度 ≥2 的純 ASCII 字母 value 有 0 筆**；純 ASCII 字母 value 共 52 筆，
  全部是 `_letter_A` → `a`/`A` 這類**單字母**，而 `rememberWord()` 對 <2 直接 return。
  全形英數（`ａ`/`Ａ`）與標點（`⒮`、`Ⓢ`）都不是 ASCII，不會命中。
  → **shipped 詞庫不會誤學**。殘留風險是使用者自訂詞（value 為英文縮寫，如 `USB`）
  被選中時會靜默學進 `latin-user.txt`（N7）。

### 10. UX 取捨 (a)–(c) — **建議：留 Rule A，砍/鎖 Rule C**

把 eval200 的 385 個英文 token 逐一跑過規則模擬：

| 判定 | shipped（minLen=2） | minLen=3 |
|---|---|---|
| Rule A（結構判死） | **342（88.8%）** | 342 |
| Rule B/C（詞典＋空白） | **19（4.9%）** | 6 |
| 兩條都沒接住 | 24（6.2%） | 37 |

- 靠 Rule B/C 的 token 只有 `AI`、`App`、`No`、`UI`、`ai`、`app` 六種。
- 接不住的 24 個幾乎全是單字母（`A B C D H I O S V X c e m p`）＋ `MM`、`zz`。

**(a) 「acer 在第 2 字母就判英文、句中無空白時無法 Tab 回中文」**
- 發生頻率：**88.8% 的英文 token 都走 Rule A**，所以「一旦進英文就出不來」
  幾乎是常態。PROBE06 直接量到：`ji3acercj04` → `我acercj案`——
  lock 之後的 `c`、`j` 被吸進英文 run，直到非字母鍵 `0` 才脫離。
- 但這**不是**放寬 Rule A 的理由：Rule A 對全部 `data.txt` 單音節 reading
  **零誤判**（維度 6），會誤觸只有「同類別自我修正」一種（N8）。
  而且 Rule A 產生的 `_latin_` 節點只有 1 個候選，Tab 對它本來就無效。
- **建議**：不要放寬 Rule A 的結構判定。改成給一個**明確的脫離手勢**——
  例如 lock 中按 Tab（目前對 `_latin_` 節點無作用）改為「把 run 退回逐鍵注音」，
  或按一次 Backspace 就整段退回。代價：多一個要教的手勢；收益：保住 88.8% 的 F1
  且不動任何規則常數。
- **真正該動的是 Rule C**：它只買到 4.9% 的 F1，卻付出純中文 −5.1pt
  的代價（維度 6）。把 `kMinAmbiguousWordLength` 提到 3 可以一次消掉
  20 個一聲衝突中的 19 個，F1 只掉約 3.4pt（19 → 6 個 token）。
  **這是明顯划算的交換，建議直接做。**

**(b) 「backspace 對未 locked 的 Ambiguous run 是整段重置」**
- 這條本身可接受（unlocked run 的字母仍在 `_bpmfReadingBuffer` 裡，
  `backspace()` 正常運作，只是 tracker 從頭觀察）。
- 真正的 bug 是 **locked** run 那一半（B5），實作者的自述沒有涵蓋到。

**(c) 「Latin-locked run 進行中方向鍵未特別處理」**
- 實測（PROBE08）**沒有掉字**：方向鍵的 `(char)charCode` 不是 8/27，
  會走 `_commitMixedScriptLatinRun()` 把 run 存進 grid，再由方向鍵處理移動游標，
  `我acer` 完整保留。這條自述的擔憂實際上是安全的。
- 但要注意這是靠 `(char)0xF702 == 0x02 != 8 && != 27` 這種**巧合**成立的
  （N11 的同一個截斷問題）。建議改成用 `input.isCursorForward` 等語意判斷。
