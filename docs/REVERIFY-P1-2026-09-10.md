### BLOCKING

#### R1. 非標準鍵盤配置（許氏／倚天26）開啟後中文輸入整體崩潰

- **位置**：`Source/KeyHandler.mm:559`
  ```objc
  BOOL mixedScriptActive = Preferences.mixedScriptEnabled && _inputMode == InputModeBopomofo && !input.isShiftHold;
  ```
  沒有任何 `Preferences.keyboardLayout` 檢查；`:567` 直接把**當前配置**餵進去：
  `_mixedScriptTracker->feedKey(_bpmfReadingBuffer->keyboardLayout(), rawKey)`。
  而 `Source/Engine/MixedScript/bopomofo_shape_tracker.cpp:49-52` 自己寫著
  「The standard layout (the only one mixedScript supports) maps every key to at
  most one component, so the first candidate is authoritative」，然後就
  `components[0]`——**這個假設在 26 鍵配置上是錯的，而且沒有任何程式碼擋**。

- **量測**（各配置用 `keySequenceFromSyllable` 從 eval200 gold readings 各自反推
  按鍵序列，逐句打進真 KeyHandler，ON vs OFF）：

  | 配置 | a–z 對應到多個 component 的鍵 | 差異句數 | ON 字元正確 | OFF 字元正確 |

  | 標準（大千） | 0 / 26 | **0/199** | 4369/4561 | 4369/4561 |

  | **倚天26** | **15 / 26**（c d f g h j k l m n p q t v w） | **199/199** | **14/4561** | 4369/4561 |
  | **許氏** | **14 / 25**（a c d e f g h j k l m n s v） | **199/199** | **15/4561** | 4369/4561 |

- **重現序列**（倚天26）：`可以看出雲地整合少了多少` 的按鍵
  `krjejkmkyx unfdekgljhrfczjlrddxo` →
  ON 輸出原封不動的 `krjejkmkyx unfdekgljhrfczjlrddxo`，OFF 輸出
  `可以看出雲地整合少了多少`。

  等於擲骰子，Rule A 的 C\*M\*V 檢查在第 2 個鍵就判死 → 每個音節都 lock 成英文。

- **修法一句**：`mixedScriptActive` 與 `:2921` 的 `mixedScriptShowsLatinRun`
  各加 `Preferences.keyboardLayout == KeyboardLayoutStandard`
  （或在 `MixedScriptTracker::feedKey` 開頭比對 `layout == StandardLayout()`，
  非標準一律回 `kChinese`）。README 已經寫「只支援標準（大千）」，但沒有程式碼執行它。

### 2. B3 —— 已關；(a) 沒破，(b) 有一條真的回歸

- `acer api gmail` + Enter → committed `acer api gmail`。
- `ji3 up jo4` → `我因為`。

- **(b) 字母選字鍵會不會被誤取消 —— 主要路徑安全，越界那一格是回歸。**

**(b) `_mixedScriptAlternates` 與 `rememberWord`**

- Tab 選英文後**只寫該詞**：`coo ` → Tab → `latin-user.txt` = `"coo\n"`。
- **重複選不重複寫**：同一個詞再選一次，檔案內容完全相同
  （`rememberWord` 在 `userWords_.insert` 失敗時就 return，`latin_lexicon.cpp:182-185`）。
- **literal space 節點不會被學**：`IsAllAsciiLetters(" ")` 為 false，Tab 之後檔案沒變。
- **寫入失敗路徑**：把 `latin-user.txt` 的位置換成一個目錄（`ofstream` 開不起來）→
  `zoo ` → Tab → 組字區仍是 `zoo`，打字沒被擋，log 出現一次
  `warning: could not persist mixedScript word to ...`，且該詞在本 session 內
  仍然生效（下次 `zoo ` 直接英文）。行為與註解一致。
- **但**：rule-A run 按 Tab 也會寫檔 → R5。

**(c) 詞表背景載入 —— publish 正確，數字對得上**

- 同步模式正確：background block 是唯一 writer，把所有寫入做完才
  `gLatinLexiconReady.store(true, release)`；`+latinLexicon` 先
  `load(acquire)`，沒 ready 就回 `nullptr`（`LanguageModelManager.mm`）。
  這是標準 publish pattern，沒有其他 reader 會在 ready 之前碰 `gLatinLexicon`。
  `fixNodeWithReading:` 的 `setUserWordListPath` 也在 ready 之後才可能執行，
  與 background thread 的同一呼叫之間有 happens-before。**沒有 race。**
- **載入中按字母鍵**：`lexicon_ == nullptr` → `feedKey` 跳過 `isWord`、
  `onBoundary` 直接回 `kChinese` → 只有 Rule A（結構檢查，不需要詞典）生效，
  safety net 也照常。不會 crash、不會掉字，只是頭 ~200 ms 內 rule B/C 不作用。
  代價是「同一串按鍵在開機頭幾百毫秒的行為與之後不同」，實務上因為 rule B
  只涵蓋 15 個詞，影響可忽略。
- **實測（`-O2`，直接連 `libMixedScriptLib.a`）**：

  | 項目 | round 1 | round 2（本次實測） |
  |---|---|---|
  | 載入 204,374 詞 | 152 ms（主執行緒） | **194.5 ms（背景執行緒）** |
  | RSS 增量 | +13.1 MB，首次 isPrefix 再 +4.8 MB | **+14.3 MB，isPrefix 後 +0.00 MB** |
  | **首次 `isPrefix()`** | **294 ms** | **0.0021 ms** ✅（回報說 0.0019 ms，同一量級） |
  | `isWord()` 熱路徑 | 0.153 µs | 0.154 µs |
  | `isPrefix()` 暖機後 | 1.233 µs | 1.240 µs |
  | `rememberWord()` 後的下一次 `isPrefix()` | 會重排 294 ms | **0.0016 ms** ✅ |

  294 ms 地雷確實拆掉了，而且是用「載入時線性 merge」而不是「刪掉 isPrefix」。
  總記憶體反而比 round 1 少（14.3 vs 17.9 MB）。

**(d) alternate 分數 `top − 1e-4` 讓 UOM 也學 —— 確認為真，且 pref 關不掉 → R6**

- 候選窗順序確認修好：`ell ` → 高，Down 後候選前 6 名
  `<高> <ell> <糕> <膏> <羔> <睪>`，`ell` 的 index = **1（第二列）**，
  共 40 個候選（round 1 是墊底第 40）。
- 走查不受影響：15 個 rule-B 詞裡尚未學過的（`ell/all/full/eel/app/aal`）
  ON 與 OFF 的預設選字完全相同（高／貓／敲／高／悶／貓）。
- **但 UOM 會學**：`fixNodeWithReading:` 的 observe 門檻是
  `currentUnigram().score() > -8`（`KeyHandler.mm:254`）。`-99` 進不去，
  `top − 1e-4` 進得去。實測序列：

  | 步驟 | 結果 |
  |---|---|
  | `ji3` + `eel ` | `我高` |
  | Tab | `我eel`（同時寫進 latin-user.txt，同時被 UOM observe） |
  | **把 `MixedScriptLatinOnSpaceForUserWords` 設 false**，重打 `ji3` + `eel ` | **`我eel`** ← pref 沒關掉 |
  | pref 仍 false，換 context：`su3` + `eel ` | `你高` |

  同樣的事在無 context 下也重現：`ull ` 學過之後，pref 設 false 仍然給 `ull`
  （因為當初就是在無 context 下 Tab 的）。
- **會不會「永遠變英文」**：不會永遠——UOM halflife 5400 s（1.5 小時）、
  容量 500 筆，而且 `selectOverrideUnigram` 要求該值必須存在於 node 的 unigram 裡
  （`reading_grid.cpp:482-493`），也就是**只有再打一次同一串字母**、alternate 被重新
  登記時才會生效，用別的按鍵打出同一個 reading 不受影響。範圍是
  (context, reading, 那串字母) 三元組。
- **需不需要 gate**：需要，但不是把 UOM 關掉——使用者確實親手選過，學起來是對的。
  真正的問題是 **pref 的名字與文件在說謊**：`Preferences.swift:342-357` 寫著這個開關
  控制「是否自動 commit 成英文」，但關掉之後仍然會自動 commit 成英文。
  最小修法：pref 文件講清楚它只管「空白自動提升」那一條，UOM 學習不歸它管；
  或在 `:254` 的 observe 條件加上「這個 node 不是 mixedScript alternate」。

### 6. N8 的不同意 —— **實作者對，而且對得比他自己說的理由更硬**

實作者拒絕「同類別自我修正視為取代」，理由是與維度 10「不放寬 Rule A」矛盾。
這個理由其實不夠有力（維度 10 講的是不放寬**結構判定**，而 N8 主張的是

`Mandarin.h:418-431` 的 `combineKey` 是把整串 key sequence 重組再 parse，
第二個聲母確實會取代第一個）。

所以我自己算了 F1。把 eval200 的 385 個英文 token 各跑三種規則：

- 首發規則分布（shipped）：`consonant-after-medial-or-vowel` 171、
