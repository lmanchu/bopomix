## 問題清單（依嚴重度）

### P-1 🔴 blocking（安裝前必修）— 換使用者詞庫資料夾會把 `latin-user.txt` 整檔覆蓋

**檔案**：`Source/Engine/MixedScript/latin_lexicon.cpp:359` ＋ `Source/KeyHandler.mm:1236-1241`
＋ `Source/AppDelegate.swift:174-185`

`persistUserWords()` 用 `std::ofstream(path, std::ios::trunc)` 把**整個** `userWords_` 記憶體
內容寫出去；`_rememberLatinWord:` 每次寫入前都重新解析路徑（`setUserWordListPath`），註解明說
「folder follows `Preferences.useCustomUserPhraseLocation`, which the user can change after the
lexicon has already loaded」。但資料夾換掉時，**沒有任何地方重新 `loadUserWordList()` 新路徑**
——`AppDelegate.updateUserPhrases()` 只重載中文使用者詞庫（`loadUserPhrases` /
`loadUserPhraseReplacement`），完全沒碰 Latin lexicon。

重現序列：
1. 在位置 A 用一段時間，`A/latin-user.txt` 累積 N 個詞
2. 偏好設定 → 自訂使用者詞庫位置改成 B（B 已有一份 `latin-user.txt`，例如 Dropbox 同步回來的）
3. 隨便打一個英文詞 + Enter（觸發 learn-from-typing）
4. `B/latin-user.txt` 被 truncate，寫入 **A 的內容**；B 原本的詞全沒了

修法一句：`_rememberLatinWord:` 發現路徑和 `userWordListPath_` 不同時先
`reset() + 重新 loadBuiltinWordList + loadUserWordList(新路徑)`，或最小修法——監聽
`userPhraseLocationDidChange` 時呼叫 `LanguageModelManager` 重載 Latin lexicon。

註：這不是 round 3 回歸，`ios::trunc` 從 `3284514`（P3 round 1）就在，上一輪 review 沒抓到。
P1 時代是 append，所以換資料夾只會合併不會刪。

### P-2 🔴 blocking（給 CI/開發流程）— parallel 測試會寫進使用者真實資料夾

**檔案**：`AGENTS.md:61-91`（N15 的處置）＋ `tools/eval/check_plist_unchanged.sh`

我照題目要求跑了一次 `-parallel-testing-enabled YES`。結果：

- plist 沒被改（`PLIST_UNCHANGED`），**但**
- `~/Library/Application Support/McBopomofo/`（跑之前不存在）被建立，
  裡面 `latin-user.txt` 1.1K，內容是 eval200 corpus 的 130 個詞、score 2：
  `irisgo 22 / google 28 / computex 12 / acer 10 / asus 10 / tony 8 / claude 8 / phison 6 …`
- 檔案 mtime `10:05:13`，parallel run 的 xcresult 是 `Test-McBopomofo-2026.09.12_10-05-08`
  ——parallel 跑起來 5 秒就寫下去了

機制：`Preferences.useCustomUserPhraseLocation` 是跨 process 共用的 defaults key。
worker A 的 teardown 還原快照（或 `PreferencesTests.reset()` 把 key 刪掉）的瞬間，
worker B 正好呼叫 `_rememberLatinWord:` → `latinUserWordListPath` 解析成**預設**資料夾 →
`ensureLatinUserWordListFolder` 直接把資料夾建出來並寫入。

也就是說：N15 被降級成「文件寫清楚就好」是不夠的。不支援的模式不會只是「報無關的失敗」，
它會污染使用者的真實輸入法資料。而 `check_plist_unchanged.sh` **只守 plist、不守資料夾**，
所以連偵測都偵測不到。

我已把該資料夾移除（內容副本留在 `/tmp/rv-leaked-latin-user.txt` 當證據），機器已回到原狀。

修法一句：`UserDefault` 的 `container` 在 `ProcessInfo.processInfo.environment["XCTestConfigurationFilePath"] != nil`
時改指向 per-process 的 `UserDefaults(suiteName:)`（約 10 行，不是 AGENTS.md 說的「real refactor」），
並把 `check_plist_unchanged.sh` 加上 `~/Library/Application Support/McBopomofo` 的存在檢查。

### P-3 🟡 round 3 新回歸 — `PreferenceSandbox` 擋不住 test host 自己寫進去的 key

**檔案**：`McBopomofoTests/PreferenceSandbox.swift:77-84` ＋ `Source/main.swift:98`

`processStartSnapshot` 是在**第一個 `install()`**（`KeyHandlerBopomofoTests.setUpWithError`）才拍的。
但 XCTest 的 test host 就是 McBopomofo.app 本體，`main.swift:98` 的
`Preferences.populateDefaults()` 在**任何測試跑之前**就已經把 23 個 key 無條件寫進真實 domain：

```
KeyboardLayout, BasisKeyboardLayout, FunctionKeyKeyboardLayout, CandidateKeys,
SelectPhraseAfterCursorAsCandidate, MoveCursorAfterSelectingCandidate,
UseHorizontalCandidateList, ChineseConversionEnabled, HalfWidthPunctuationEnable,
SelectCandidateWithNumericKeypad, Big5InputEnabled, ChineseConversionStyle,
PhraseReplacementEnabled, AssociatedPhrasesEnabled, LetterBehavior, ControlEnterOutput,
ShiftEnterEnabled, RepeatedPunctuationToSelectCandidateEnabled,
AddPhraseHookEnabled, AddPhraseHookPath, BeepUponInputError,
EnableUserPhrasesInPlainBopomofo, AllowMovingCursorWhenChoosingCandidates
```

加上 `AppDelegate` 啟動時的 `BopomofoFontAnnotationSupportMenuItemEnabledByInstalledFontsCheck_V1`、
`CheckUpdateAutomatically` / `NextUpdateCheckDate`（`checkForUpdate()`）。
這些 key 因為早於快照，全部被「還原」而不是被移除。

**這算不算污染：算，而且有實害。** 你機器上現在的值是：

```
AddPhraseHookPath = ~/dev/mixime/build/Build/Products/Debug/McBopomofo.app/Contents/Resources/add-phrase-hook.sh
```

安裝的輸入法在 `~/Library/Input Methods/McBopomofo.app`，這個路徑只可能是測試 host 寫的。
`AddPhraseHookEnabled` 目前是 false 所以沒作用，但只要你哪天打開 add-phrase hook，
輸入法會去執行 build 目錄裡的 script——那個目錄 `git clean` / 重 build 就會消失。

`CustomUserPhraseLocation=""` / `UseCustomUserPhraseLocation=0` **不在** `populateDefaults()` 名單裡，
只有掛 sandbox 的四個 class 會寫。在序列模式下 sandbox 會正確移除它們（我實測 4 次 serial run，
其中一次有真實失敗，plist 三次 diff 全部 identical）。你觀察到它們被補進去，最可能是
parallel run 的競態（各 worker 各拍各的快照，B 拍到 A 設好的值就永久還原回去），
次可能是 runner crash（crash 的 process 完全不跑 teardown block）。

實測「跑完實際新增的鍵」：**0 個**（serial 模式、你機器目前狀態）。
但這是因為上面那些 key 早就被先前的測試補進去了，不是因為 sandbox 有擋住。

修法一句：把快照改成在 `McBopomofoTests` 的 bundle `+load` / `XCTestObservation.testBundleWillStart`
拍——還是晚於 host 的 `main`；真正正確的作法是 P-2 的 per-process suite。
最低成本的補救是在 sandbox 還原後，額外移除一份「host 會寫但使用者未必有」的 key 白名單。

### P-4 🟡 round 3 新回歸 — N2 修正後的「62% 是排序問題」被高估

**檔案**：`McBopomofoTests/LatinCompletionKeyHandlerTests.swift:1026-1037`（`simulateCompletion`）
＋ `:1113-1122`（`classify`）＋ `tools/eval/BASELINE.md` P3 段

`simulateCompletion` 是打進**真的** `KeyHandler`，所以一個 Bopomofo 形狀一直合法、
Rule A 從來沒 lock 的 token（`app`、`API`、`CLI`、`SOW`、`SLA`、`you`、`com`、`GPU`、`Tool`）
根本不會出現 tooltip。它被記成 never completable，然後因為小寫形在詞典裡，
被 `classify` 歸類成 **rankingMiss**。

我重跑這段（自己解析 corpus、走真 KeyHandler）得到：

| | 值 |
|---|---|
| eligible tokens | 330（與 BASELINE 一致） |
| never completable | 155（一致） |
| ranking miss | 96（一致） |
| **其中「從未 lock 成 Latin run」** | **15** |

所以「62% of never-completable tokens are ranking misses → P4 該去找 frequency source」
實際上是 **81/155 = 52%**；另外 15 個是 Rule A 覆蓋率問題，再好的詞頻資料也救不了。
BASELINE.md 的那句結論要改。

另外同一段（`:1222-1225`）"with history" pass 用的是
`handler.acceptLatinCompletion(value:)`（`kExplicitAcceptWeight` = 2，一次就 confirmed），
但散文寫的是「the same way `Preferences.latinLearnTypedWords` does in production」。
production 的規則是詞典詞 weight 1、非詞典詞要兩次才落地。**"with history" 的 48.8% 是樂觀值**，
不是生產行為。

修法一句：`simulateCompletion` 回傳「是否曾 lock」，`classify` 多一類 `neverLocked`；
散文把 "the same way ... does in production" 改成 "with a single explicit accept (optimistic upper bound)"。

### P-5 🟢 non-blocking — Rule-B alternate 的 Tab 不套 B3 gate

**檔案**：`Source/KeyHandler.mm:1642-1650`

```objc
if (isRuleALiteralNode) {
    offered = [self _offeredCompletionFor:value lexicon:lexicon];
} else {
    std::vector<std::string> top1 = lexicon->complete(value, 1);   // 沒有 gate
    ...
}
```

作者在註解裡明說這是刻意的（「gating it here would silently stop e.g. "coo" from completing
further into "cook"」）。後果：任何經由候選窗選成英文的詞，再按一次 Tab 會被無條件展開成
top-1 completion，即使它本身已經是 finished word。

實測確認 `coo` 這條路徑無法用現有 test harness 走（選候選需要 `VTCandidateController` delegate），
所以這條是**靜態確認**：離線重建 lexicon 得到 `complete("coo",1) = cookie`（seed rank 265），
而 `sourceTier(coo) = sourceTier(cookie) = 1`，Rule-A 路徑判定為 finished（我實測 tooltip 為空）。
兩條路對同一個字給出相反答案。

判斷：**作者的取捨我不同意**。理由不是 "coo"（沒人打），是「同一個字在兩條路徑下行為相反」
本身就是使用者學不會的規則。但它不會弄壞資料，也不會影響中文，所以 non-blocking。

修法一句：Rule-B 分支也套 `_offeredCompletionFor:`，把 `cook` 那個例子當作已知損失接受。

### 2. B2 — 學習政策實測表

**已關。** 全部走真 `KeyHandler`，讀 throwaway 資料夾裡真實的 `latin-user.txt`。

| 序列 | `latin-user.txt` 實際內容 | 預期 | 結果 |
|---|---|---|---|
| `the` + Enter（詞典詞，一次） | `the→1` | 立刻寫、score 1 | ✅ |
| `thq` + Enter（非詞典詞，第 1 次） | 空 | 不寫 | ✅ |
| `thq` + Enter（第 2 次，另一次 commit） | `thq→2` | 寫入、帶著 sightings | ✅ |
| `aweso` + Tab + Enter | `awesome→2`，**只有一筆** | 只寫被接受的字、weight 2 | ✅ |
| 40 個字母 + Enter | 空 | 超過 20 上限 | ✅ |
| `th` + Enter | 空 | 低於 3 下限 | ✅ |

| Shift+T/H/E + Enter | 空 | 大寫路徑看不到這個 hook | ✅ |
| `su3`（你）+ Enter | 空（committed = 你） | 中文永不寫 | ✅ |
| `latinLearnTypedWords = false`，the/thq/thq | 空 | 零寫入 | ✅ |
| `latinCompletionEnabled = false`，the/thq/thq | 空 | 零寫入（N3） | ✅ |

**pending 計數跨 session 會不會消失：會，而且我實測了。**
`pendingTypedWords_` 只活在 process 內的 `LatinLexicon`（`latin_lexicon.h:282`，
明寫 in-memory only, never persisted）。我用 `resetLatinLexiconForTesting()` +
`loadDataModels()` + 新 `KeyHandler` 模擬輸入法 process 重啟：
`thq` 第 1 次 → 重啟 → `thq` 第 1 次 → `latin-user.txt` 仍然是空的。

**這個設計對真實使用有效嗎——我的判斷：對「防污染」有效，對「學新詞」幾乎無效。**

- 有效的一面：它擋掉的正是 B2 的原始災難（一個 typo 或一段吃掉中文鍵的 run 永久霸佔 prefix）。
  單次目擊永遠不落地，這點做對了。
- 無效的一面：macOS 輸入法 process 會因為登出、切換輸入法、當機、系統更新而重啟，
  而「兩次」必須在**同一個 process 生命週期內**湊到。真正的新詞（人名、產品名、內部代號）
  往往一天只打一兩次、中間隔了好幾小時。實務上很多合法新詞永遠湊不到第二次。
- 結果是：**詞典裡有的字一次就學（而且你打兩次就會壓過整本詞典），詞典裡沒有的字
  ——也就是唯一真正需要學的那些——反而學不進去。** 這是反過來的。
- 修法建議（非 blocking）：pending 計數落地成一個小檔（`latin-pending.txt`），
  或改成「非詞典詞第一次就以 score 1 寫入，但 score 1 不參與 `complete()` 排序」
  ——後者其實現有程式已經支援（`kUserWordConfirmedScore` 就是幹這個的），
  等於把記憶體 staging 換成磁碟 staging，行為不變、跨重啟有效。

### 4. B4 — `the` + Shift+A

**已關。** 提交的文字是 `the`，而且 `handle(input:state:...)` 回傳 **NO**。

這是正確的：`Source/KeyHandler.mm:668-688` 先把 pending run commit 進 grid 並發出
`Inputting("the")`，接著 upstream 的大寫路徑（`:1136-1150`，`letterBehavior == 0`）
`[self clear]` + 發 `Empty`——`InputMethodController` 在進 `Empty` 時提交前一個狀態的
composing buffer，所以 `the` 真的送進 app 了。然後 return NO，大寫 `A` 由 app 自己打出來。
最終使用者看到 `theA`。（測試 harness 看不到 app 自己打的那個 `A`，所以斷言寫成
「committed == "the" 且 consumed == false」。）

順帶驗到：這一次 commit 也會 learn（`mayLearn:YES`），`the→1` 有寫進去。

**候選窗開著時 Shift+字母**：`th` + Shift+Tab（候選窗）+ Shift+A →
`_handleLatinCompletionCandidateState:` 走「關窗 + 重新 dispatch」分支，
重新 dispatch 進 B4 分支 → commit `th` → 大寫路徑 → return NO。
committed = `th`，consumed = false。正確。
